
## 表 2 · `calendar.csv` —— 房源日历

> 🔴 **差异 A（本地核对）**：2026-06-14 快照的 calendar **只有 5 列，不含 `price`**。
> 这与绝大多数公开教程和旧版资料不符 —— **价格分析必须完全依赖 `listings` 表**。

| 字段 | 含义 | 备注 |
|------|------|------|
| `listing_id` | 外键 | Join 到 `listings.id` |
| `date` | 日期 | 覆盖**未来 365 天**，**无历史** → **发现 18** |
| `available` | `t` / `f` | ⚠️ **`f` ≠ 已出租**（见陷阱 #2） |
| `minimum_nights` | 该日期适用的最短入住 | ⚠️ **逐日变化**，与 listings 不同 |
| `maximum_nights` | 该日期适用的最长入住 | 逐日变化 |

**本快照已移除的字段（旧资料中存在）**：`price`、`adjusted_price`

> 🔥 **`calendar` 只包含未来日期，不含历史。**
> 意味着"过去这一年被订了多少天"无法直接观测 —— 这是出租率必须依赖估算的根本原因。

### 🆕 差异 B · `listings` 新增 `price_quote_*` 系列

本快照新增 6 个价格报价字段（旧资料中不存在）：

| 字段 | 含义 | 备注 |
|------|------|------|
| `price` | 房源标价 | ⚠️ 字符串 `"$150.00"`，需清洗 |
| `price_quote_checkin_date` | 询价入住日 | 平台用一次示例查询取得报价 |
| `price_quote_checkout_date` | 询价离店日 | |
| `price_quote_total_price` | 示例住期的**总价** | |
| `price_quote_price_per_night` | 示例住期的**每晚均价** | ⭐ 可能比 `price` 更接近真实成交价 |
| `price_quote_raw` | 原始报价文本 | 含清洁费、服务费等拆解 |

> ⭐ **这是相对 `price` 更可靠的定价字段** —— `price` 是房东设定的挂牌价，
> 而 `price_quote_*` 是平台实际报给客人的价格（含各类费用）。
> 分析时应以 `price_quote_price_per_night` 为主口径，`price` 作为对照。

### 🆕 差异 C · `listings` 直接提供出租率与收入估算

本快照新增（旧版需自行计算）：

| 字段 | 含义 |
|------|------|
| `estimated_occupancy_l365d` | **过去 365 天估算出租间夜数**（Inside Airbnb 代算） |
| `estimated_revenue_l365d` | **过去 365 天估算收入** |

> ⭐ **这改变了项目的方法论定位。**
> 原计划：自行用 San Francisco Model 计算出租率。
> 调整后：**以官方估算值作为基准，自行复现并验证其一致性** ——
> 既能证明理解方法论，又能发现官方估算的偏差边界，比单纯调用现成字段高一个层级。
> 自有 M1–M4 敏感性分析仍然保留，用于验证结论稳健性。

### 🆕 其他新增字段

| 字段 | 含义 | 价值 |
|------|------|------|
| `license` | **短租经营许可证号** | ⭐ 监管分析金矿（NYC 有严格短租法规） |
| `instant_bookable` | 是否支持即时预订 | 运营策略变量 |
| `has_availability` | 当前是否有可订日期 | 判断"僵尸房源"的关键 |

| `hosts_time_as_host_years` / `_months` | **成为房东的时长（已算好）** | 免去手工计算 |
| `hosts_time_as_user_years` / `_months` | 作为用户的时长 | |

| `host_profile_id` / `host_profile_url` | 房东资料页 | |

## ⚠️ 七个必踩的坑

| # | 坑 | 后果 | 详见 |
|---|-----|------|------|
| 1 | `price` 是字符串 `"$150.00"` | 直接 `.sum()` 得到字符串拼接 | 清洗时处理（Phase 5） |
| 2 | `available = f` 被当作出租 | 系统性高估需求 | **发现 1** |
| 3 | `host_listings_count` / `host_total_listings_count` / `calculated_host_listings_count` 三兄弟 | 算"房东规模"时选错，结论全偏 | **发现 16** |
| 4 | `number_of_reviews` 是累计值 | 老房源数值天然偏高，不可直接横比 | **发现 17** |
| 5 | `neighbourhood` 未清洗 | 分组时同一街区被拆成多个 | **发现 19**（另见发现 6：本快照该字段已全空） |
| 6 | `calendar` 只有未来 | 想算历史出租率会扑空 | **发现 18** |
| 7 | `property_type` 有 30+ 类 | 不归并则图表无法阅读 | **发现 20** |

> 📎 **本表的详细展开在 [`insights_collection.md`](insights_collection.md)** —— 每条坑的完整证据与影响都在那边。本表只作速查索引。

### 实际行数（2026-06-14 快照）

| 表 | **真实记录数** | 物理行数(`wc -l`) | 与预估值对比 |
|---|--------------|-----------------|-------------|
| `listings` | **30,259** | 54,270 ⚠️ | 预估 3 万 → 基本吻合 |
| `calendar` | **11,152,576** | 11,152,577 | 预估 700 万 → 实际高出 59% |
| `reviews` | **990,170** | 990,171 | 预估 100 万 → 基本吻合 |

> 🚨 **`listings` 的两个数字不一样，差 24,011。**
> `wc -l` 数的是**物理换行符**，而 `listings` 的多行文本字段
> （`description`、`amenities`、`host_about` 等）内部含有换行。
> **pandas 和 Python 的 csv 模块会正确处理引号内的换行，得到 30,259 —— 这才是真实记录数。**
>
> **教训：统计 CSV 行数不能用 `wc -l`。** 用 `len(pd.read_csv(...))` 或 `sum(1 for _ in csv.reader(...))`。

> 💡 **另一条教训**：项目规划阶段的"预估值"来自二手资料，与真实数据存在系统性偏差。
> **规模预估必须以实际数据为准**，因为它直接决定技术选型（内存、索引、分块策略）。

> 🎯 **注意 `host_verifications` 的特殊性**：
> 其余 11 个字段是**真的空**，但 `host_verifications` 里装的是**字符串 `"None"`** ——
> 即 Python 的 `None` 被序列化成了文本。
>
> pandas 默认会把 `"None"` 当作缺失值处理（它在该默认 `na_values` 列表中），
> 所以 pandas 读出来也是 NaN，**但原因完全不同**。
>
> ⚠️ **隐患**：如果某个字段里合法地出现了文本 "None"、""、'NA'、'NULL'、'N/A' 等，
> pandas 会**静默地**把它吃掉变成 NaN。遇到可疑的缺失率，要用 `csv` 模块读原始值交叉验证。

> 📌 **原因推测**：Inside Airbnb 近年持续缩减公开的房东个人数据（隐私合规）。
> 这类字段消失是趋势，不以个人意志为转移 —— **项目规划必须留出"字段可能不存在"的余地**。
