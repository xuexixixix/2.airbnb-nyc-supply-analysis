# 方法论 · 出租率估算

> 本文记录本项目**最核心的数据口径决策**。
> 本文件记录最核心的数据口径决策 —— "这个出租率是怎么算出来的"，答案出自这里。

---

## 一、问题：为什么不能直接用日历算出租率？

`calendar.csv` 提供一个看起来很像出租率的字段：`available`（`t` / `f`）。

直觉做法：

```python
# ❌ 错误做法
occupancy = (calendar['available'] == 'f').mean()
```

**这个做法是错的。** Inside Airbnb 官方文档明确说明：

> "The Airbnb calendar for a listing **does not differentiate between a booked night vs an unavailable night**, therefore these bookings have been counted as 'unavailable.'"

即 `available = f` 混合了**两类性质完全相反**的情况：

| `f` 的真实原因 | 业务含义 | 是否应计入出租 |
|---------------|---------|--------------|
| 被客人预订 | **真实需求** | ✅ 是 |
| 房东手动关闭日历 | **供给主动退出** | ❌ 否 |

一项将日历数据与房东后台真实预订状态匹配的研究（Berkeley Haas / SICS）测得实际分布：
**27% 真实预订、34% 可订未售、39% 房东封锁。**

**结论**：直接把 `f` 当出租，会**系统性高估需求**，且高估幅度无法从数据内部校正。

---

## 二、解法：基于评论数反推（San Francisco Model）

平台不公开订单数据，学界与业界通行的方案是使用**代理指标** —— 评论数。

**逻辑链**：评论是入住后的行为 → 评论数正比于订单数。

Inside Airbnb 官方公布的算法（**San Francisco Model**）：

```
第 1 步  估算订单数 = 最近 12 个月评论数 × 2
         理由：假设约 50% 的客人会留评论 → 订单数 = 评论数 ÷ 0.5 = 评论数 × 2

第 2 步  单笔住宿天数 = max( 城市平均住宿天数 , 该房源 minimum_nights )
         旧金山公开值为 5.5 晚；无公开值时默认 3 晚

第 3 步  估算入住间夜 = 估算订单数 × 单笔住宿天数

第 4 步  出租率 = 估算入住间夜 ÷ 全年可订天数

第 5 步  截断：
         ├ 上限 70%   （Inside Airbnb 官方，防高估）
         └ 且 ≤ 365 ÷ minimum_nights （物理上限，防离谱值）
```

### 字段选择说明

| 选择 | 理由 |
|------|------|
| 用 `number_of_reviews_ltm` 而非 `number_of_reviews` | 累计值受房源注册时间影响 |
| 用 `number_of_reviews_ltm` 而非 `reviews_per_month` | 后者基期不明；前者为固定 12 个月窗口，不受注册时间与季节性影响 |

### 为什么评论率取 50%？

| 候选值 | 来源 | 评价 |
|--------|------|------|
| 72% | 出自 Airbnb CEO 的公开表述 | 无法验证，被认为过于乐观 |
| 30.5% | 由公开评论数据与 2014 年纽约总检察长报告比对得出 | 更基于事实，但未考虑已删除房源的评论缺失，不够保守 |
| **50%** | Inside Airbnb 采用 | **几乎正好落在 72% 与 30.5% 之间** |

## 三、稳健性验证：四方法敏感性分析

源自一项对爱丁堡数据的学术研究，将估算分为四个严格程度递增的版本：

| 方法 | 公式 | 严格程度 |
|------|------|---------|
| **M1** | `reviews × min_nights` | 最保守（不乘 2） |
| **M2** | `(reviews / 0.5) × min_nights` | 中等 |
| **M3** | `reviews × max(avg_stay, min_nights)` | 较激进 |
| **M4** | `(reviews / 0.5) × max(avg_stay, min_nights)` | 最高估 |

原研究结论：**四种方法算出的绝对值差异很大，但彼此显著正相关。**
因此该方法适用于**相对比较**（A 街区 vs B 街区、专业房东 vs 个体房东），
**不适用于报告绝对值**。

## 四、已知局限（必须写进报告）

1. **系统性偏差，非随机噪声**
   一项独立测量曼哈顿的研究发现真实评论率约为 **55%**（本项目采用保守的 50%），
   且**价格越高、预订越频繁的房源，评论率越低、平均住宿天数越长**。
   这意味着偏差方向可能与部分分析口径一致，**可能放大跨类型对比的差异**。

   → 处理方式：结论只在**同类型房源内部**比较；跨类型对比须标注不确定性。

2. **上限带来的截断偏差**
   出租率超过 70% 的房源被截断，因此**最繁忙的房源会被系统性低估**。

3. **快照性质**
   所有指标基于单次快照，无法反映趋势变化。

4. **代理指标的固有损耗**
   并非所有入住都产生评论，也并非所有评论都对应一次入住（存在一次入住多条评论的情况）。

## 五、口径选择说明

> "我原本打算直接用日历里的 `available` 字段算出出租率。
> 但在跑之前我先做了一次常识校验 —— 我发现 `available = f` 既可能是被订走了，也可能是房东自己关闭了日历。
> 这两件事在业务上完全相反：前者是需求，后者是供给退出。
>
> 我去查了 Inside Airbnb 的官方文档，确认了这个字段确实无法区分二者。
> 所以我改用了官方公布的 San Francisco Model，基于评论数反推订单数，
> 并且跑了四种不同的估算方法做敏感性对比，验证我的结论在四种假设下都成立。
>
> 这个经历让我意识到：**拿到一个字段，要先搞清楚它的采集方式，再决定它能回答什么问题。**"
